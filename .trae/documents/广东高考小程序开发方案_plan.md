# 广东省2027年高考历史信息查询推荐 小程序开发方案

> 本文档只做分析与规划，不含代码实现。确认方案后再进入开发。

## 一、数据分析结论

### 1.1 数据资产清单

| 文件 | 大小 | 行数 | 字段 | 说明 |
|---|---|---|---|---|
| 广东高考物理类(2021-2026)高校录取分数.csv | 942 KB | 17,742 | 年份、院校代码、院校名称、专业组代码、计划数、投档人数、投档最低分、投档最低排位 | 1,084 所院校；各年行数：2021:2452 / 2022:2282 / 2023:2434 / 2024:2891 / 2025:3503 / 2026:4180 |
| 物理类一分一段表(2021-2026)总表.csv | 72 KB | 3,592 | 年份、分数、本段人数、累计人数(=全省位次) | 每年约 600 行，覆盖全部有效分数段 |
| 院校专业选科要求.csv | 9.9 MB | 84,378 | 地区、院校代码、院校名称、层次、专业(类)名称、首选科目要求、再选科目要求、包含具体专业 | 2,085 所院校；本科 50,127 条 / 专科 34,250 条 |

选科要求表的关键分布：
- 首选科目：物理或历史均可 57,289 条；仅物理 27,088 条
- 再选要求：不提科目要求 59,879 条；化学必选 22,812 条；化学+生物均须 502 条；其余为思政/地理/生物等小比例

### 1.2 录取数据趋势特征（2021-2026）

各年专业组、院校与招生规模：

| 年份 | 专业组数 | 招生院校数 | 计划总数 | 投档总数 |
|---|---|---|---|---|
| 2021 | 2,452 | 866 | 181,553 | 181,404 |
| 2022 | 2,282 | 857 | 172,084 | 171,051 |
| 2023 | 2,434 | 884 | 186,934 | 185,501 |
| 2024 | 2,891 | 938 | 195,709 | 190,181 |
| 2025 | 3,503 | 1,001 | 236,893 | 218,024 |
| 2026 | 4,180 | 1,055 | 243,617 | 235,964 |

关键趋势：

- **专业组数量持续扩容**：6 年间从 2,452 个增至 4,180 个（+70%），2024 年后明显加速，说明院校在粤招生的专业组划分越来越细，志愿填报的颗粒度逐年提高。
- **招生计划总体增长**：从 18.2 万增至 24.4 万（+34%），物理类录取容量在扩大；2022 年是唯一计划数回落的年份（-5.2%）。
- **每年都有院校未招满**：投档数均低于计划数，缺口在 149～18,869 人之间（2025 年缺口最大，2026 年回落至约 7,653 人），这类专业组是"保"档推荐的重要来源，界面上可对"近年多次缺额"的专业组做标注。
- **院校覆盖范围扩大**：在粤物理类招生院校从 866 所增至 1,055 所；其中 **766 所院校连续 6 年均有录取数据**，是数据连续性最好、最适合做多年趋势分析与位次法推荐的核心院校集合。

2026 年各专业组按投档最低分的分布（4,178 个有有效分数的组）：

| 分数段 | 专业组数 | 占比 |
|---|---|---|
| 650 分以上 | 51 | 1.2% |
| 600-649 | 474 | 11.3% |
| 550-599 | 961 | 23.0% |
| 500-549 | 1,418 | 33.9% |
| 450-499 | 1,091 | 26.1% |
| 450 以下 | 183 | 4.4% |

- 专业组最密集的区间是 **500-549 分（约 34%）**，中段考生可选范围最大，但同分段的专业组扎堆，位次区分比分数区分更重要——这也印证了推荐算法必须按位次而非分数匹配。
- 高分段（600 分以上）专业组仅约 12.5%，头部选择面窄，推荐时应放宽到全国院校，并更明确地提示"冲"的风险。

### 1.3 数据质量问题（开发前必须清洗）

1. **截断显示值**：顶尖院校显示为 `683以上` / `178以内`（北大、清华等）。需解析为数值 + "封顶/封底"标记，不能当普通文本。
2. **零投档记录**：部分专业组 `投档人数=0`，分数和排位为空（如长春工程学院 2021 组202）。这类记录不能参与推荐，只可展示"当年无人投档"。
3. **专业组代码缺失**：有 3 行专业组代码为 `-`（2021年北大、清华，新高考首年未公布组代码），需特殊处理。
4. **再选科目要求是长文本**：如 `化学(1门科目考生必须选考方可报考)`、`化学,生物(2门科目考生均须选考方可报考)`，必须归一化为结构化科目集合。
5. **缺少院校维度属性**：录取分数表没有 985/211/双一流、办学性质（公办/民办/中外合作）、院校所在地区等字段——而这些是用户筛选志愿的核心条件，需要额外补充一张"院校属性表"。
6. **两表院校数不一致**（1,084 vs 2,085）：正常现象，选科表含大量专科及不在粤物理类招生的院校，推荐时以录取表为准。
7. **口径年份**：2021 年是广东"3+1+2"新高考首年，专业组模式刚启用，部分数据口径与后续年份略有差异，做多年份对比时要留意。

### 1.4 数据规模对小程序的硬性约束

- 小程序主包上限 **2 MB**，全部包（含分包）上限 20 MB。
- 9.9 MB 的选科要求 CSV **不能进主包**，精简后也应放分包或云端。
- 录取表（942KB CSV，转紧凑 JSON 后预计 500~700KB）和一分一段表（约 30KB JSON）适合本地打包，可支撑离线查询。

## 二、参考的开源项目与流行产品

1. **gaokao-pro**（MIT 协议开源，github.com/HA7CH/gaokao-pro）
   - 值得借鉴：冲/稳/保推荐算法、分数↔位次换算、数据 schema 设计；
   - 其离线索引把 3,145 所院校压缩到约 1MB（gzip），证明"本地装下全部院校核心数据"完全可行；
   - track 维度设计 `physics / history / combined / science / liberal`，与本项目"目前只有物理类、后续增加高考类别"的需求天然对应，直接采用这一维度建模。
2. **掌上高考静态数据接口**（static-data.gaokao.cn）：可作为 985/211/双一流、办学性质、院校地区等属性数据的补充来源。
3. **阳光志愿信息服务系统**（教育部官方，gaokao.chsi.com.cn/zyck）：参考其产品流程"输入成绩 → 选择偏好 → 生成志愿报告"，以及官方免责边界的表述方式。注意：官方声明从未授权任何同名 APP/小程序，本项目命名与宣传不得借用"阳光高考/阳光志愿"名义。
4. **市面主流志愿小程序通用形态**：分步表单录入、录取概率高/中/低三档、按院校类型/地区/专业方向筛选、本地收藏。

## 三、产品方案

### 3.1 功能模块（对应用户三大需求）

| 模块 | 对应需求 | 内容 |
|---|---|---|
| M1 位次查询 | 需求2 | 输入分数 → 查一分一段表得当年位次；并给出**历年同位分**（同一位次在2021-2026各年对应的分数） |
| M2 志愿推荐 | 需求1 | 输入分数（或直接输入位次）+ 再选科目 + 偏好（地区、院校层次、办学性质、专业方向、志愿数量）→ 以**院校专业组**为单位输出冲/稳/保名单，标注录取概率 |
| M3 院校查询 | 需求3 | 按名称/代码搜索院校 → 院校详情：历年各专业组投档分与最低排位、分数/位次趋势图、计划数、选科要求 |
| M4 收藏 | 辅助 | 收藏院校/专业组，本地存储（wx.storage） |
| M5 数据说明 | 合规 | 数据来源、覆盖年份、更新时间、口径说明、免责声明 |

### 3.2 页面规划（原生小程序）

- `pages/index` 首页：三大功能入口 + 分数快速查询卡片
- `pages/rank` 位次查询：分数 → 位次 + 历年同位分表
- `pages/recommend` 志愿推荐：表单录入（分步或单页）
- `pages/recommend-result` 推荐结果：冲/稳/保分区列表，可点进专业组详情
- `pages/school-search` 院校搜索：名称/代码搜索 + 筛选
- `pages/school-detail` 院校详情：历年专业组表格、趋势小图、选科要求
- `pages/favorites` 我的收藏
- `pages/about` 数据说明与免责声明

### 3.3 核心算法：等位次法（重点）

**历年分数不能直接比较**（每年试卷难度、分数线、招生计划都在变），行业通行做法是"等位次法"——比位次，不比裸分：

1. 用户输入分数（2027届考生当前只能给模考分）→ 查**最新2026年一分一段表**得到预估位次，界面明确标注"基于2026年位次估算"。
2. 拿该位次直接与 2021-2026 各年专业组的"投档最低排位"比较（位次跨年可比）。
3. 冲稳保分档（按位次差比例，阈值做成可配置）：
   - **冲**：专业组最低排位比用户位次高 0~15%（即用户位次略低于该组，有机会但不稳）；
   - **稳**：用户位次优于专业组排位 0~20%；
   - **保**：用户位次优于专业组排位 20% 以上。
4. 多年份稳定性校验：近 3 年至少 2 年有可比数据才纳入，避免单年偶然波动；近年数据权重更高。
5. 录取概率高/中/低：综合位次余量大小和历年位次波动幅度给出，文案上只使用"参考概率"，不做录取承诺。
6. 志愿数量支持多档（如 20/40/80 个专业组），冲稳保按比例分配。

### 3.4 选科要求归一化与匹配

- 归一化结构：`{ first: 'physics_only' | 'any', reselect: { mode: 'none' | 'all', subjects: ['化学', ...] } }`
  - "不提科目要求" → `mode:'none'`
  - "化学必选" → `mode:'all', subjects:['化学']`
  - "化学,生物均须" → `mode:'all', subjects:['化学','生物']`
- 匹配规则：考生再选科目集合包含要求集合方可报考；首选物理的考生只需在"仅物理 / 物理或历史均可"两组中筛选。

## 四、技术方案

### 4.1 技术选型

- **保持原生微信小程序 + TypeScript**：现有脚手架已是官方 TS quickstart（含 appid、typings），原生框架文档最全、踩坑资料最多，对第一次做小程序开发最友好，不引入 Taro 等额外构建链。
- **离线数据构建脚本**（Node.js，`scripts/build-data.mjs`）：读取 data/ 内 CSV → 清洗归一化 → 输出紧凑 JSON + 数据版本清单（年份、科类、生成时间）。数据更新（如加历史类、加2027年）只需重跑脚本，业务代码不改。
- **数据存放分两阶段**：
  - v1（推荐）：核心数据本地打包——录取表 + 一分一段 + 院校属性放主包；精简后的选科表放**分包**，进入院校详情/推荐时按需加载；
  - v1.1（可选）：选科表迁到**微信云开发数据库/云存储**，年度更新数据无需重新发版审核；推荐结果在云端计算。
- 收藏、用户输入的分数/选科用 wx.storage 本地持久化。

### 4.2 数据模型（TypeScript 接口草案）

```ts
type Track = 'physics' | 'history'; // 可扩展: combined | science | liberal

interface School {
  code: string;            // 院校代码（主键）
  name: string;
  region: string;          // 省份/地区
  level: '本科' | '专科';
  nature?: string;         // 公办/民办/中外合作（待补充）
  tags?: { c985?: boolean; c211?: boolean; dualClass?: boolean };
}

interface AdmissionRecord {
  year: number;
  schoolCode: string;
  groupCode: string;       // 专业组代码
  plan: number;            // 计划数
  admitted: number;        // 投档人数
  minScore: number | null;
  minRank: number | null;
  flags: { scoreCapped?: boolean; rankCapped?: boolean; noAdmission?: boolean };
}

interface RankRow { score: number; count: number; cumulative: number; }

interface SubjectRequirement {
  schoolCode: string;
  level: string;
  category: string;        // 专业(类)名称
  first: 'physics_only' | 'any';
  reselect: { mode: 'none' | 'all'; subjects: string[] };
  majors: string[];        // 包含具体专业
}
```

## 五、实施步骤（依赖排序）

1. **补充院校属性表**：从公开静态数据源整理 985/211/双一流、办学性质、地区字段，落为一张 CSV 或构建脚本内维护。
2. **编写数据构建脚本**：三张 CSV 的清洗、截断值解析、选科长文本归一化、JSON 压缩输出；内置校验断言。
3. **服务层开发**：data-service（加载/缓存）→ rank（位次/同位分）→ subject（选科匹配）→ recommend（冲稳保）。
4. **页面开发**：首页 → 位次查询 → 院校搜索与详情 → 志愿推荐与结果 → 收藏 → 数据说明。
5. **真机与性能验证**：长列表分页/懒加载、包体积检查、分包加载验证。
6. **合规收尾**：数据来源标注、免责声明、审核类目核对。

## 六、依赖与注意事项

- **审核与类目**：志愿填报属教育信息服务，审核较敏感；个人主体部分教育类目受限。定位建议为"**历史数据查询工具**"，不做收费指导、不承诺录取、不收集身份证/准考证等敏感信息。
- **口径明示**（吸取同类项目教训）：模考分/高考分、使用了哪一年的位次表，界面必须明确标注；数据记录保留 year、track、数据版本、last_updated 字段。
- **2027 新选科要求**：现选科表为 2024-2026 版，2027 年起改用新版（省考试院 xkcx2027 系统），需在 2027 年招生季前重新抓取并更新。
- **数据更新机制**：2027 年 6 月后补充当年录取数据，靠"数据版本清单 + 重跑构建脚本"完成；若上云则可免发版。
- **包体积红线**：开发过程中持续检查主包 ≤2MB，必要时把选科数据全部下沉分包。

## 七、验证方案

- 数据校验断言（构建脚本内）：
  - 2021 物理类本科线 432 分 → 累计 222,304 人；
  - 2026 物理类本科线 425 分 → 累计 303,919 人；
  - 所有年份位次单调不减、分数连续无缺漏。
- 算法抽查：选若干已知分数（高分/中段/压线）人工核对位次与冲稳保分档结果。
- 边界测试：零投档专业组、`683以上`截断值、低于一分一段表底的分数、专业组代码缺失。
- 真机：启动速度、推荐结果滚动性能、分包首次下载体验。

## 八、风险与应对

| 风险 | 应对 |
|---|---|
| 小程序审核不通过（志愿类敏感） | 定位为数据查询工具，去除"保录取"类表述，完备免责声明与来源标注 |
| 包体积超限 | 选科数据分包/上云；构建脚本做极致压缩 |
| 历史数据本身有误 | 校验脚本 + 官方数字锚点 + 应用内反馈入口 |
| 推荐名单雷同造成误导 | 概率措辞保守、展示多年数据让用户自行判断、强调"以官方招生计划为准" |
| 新手开发复杂度 | 先本地数据后上云；先跑通位次查询单一闭环，再迭代推荐 |

## 九、待确认的关键决策（建议默认值）

1. 院校属性（985/211/办学性质/地区）：**建议**从公开静态数据源补充——是否同意？
2. v1 数据形态：**建议**本地打包 + 选科分包，暂不做云开发（零成本、先跑通）。
3. 是否需要"志愿方案导出为图片"功能：建议放到 v1.1，v1 先不做。
4. 2027 新版选科要求：建议等官方数据稳定后（2027 年上半年）再抓取更新。
